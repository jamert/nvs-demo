# How to evaluate Nevis search

**Start by writing 12 tasks an advisor should be able to complete.** The task tells you what a correct result is; the query alone often doesn't. For example, “Find Jordan Lee using this exact email” has one right result. “Find Jordan Lee” may have two plausible results. Those cases should not be scored the same way.

1. **Write the tasks and the queries.** Start with 4 client lookups (name, exact email, partial email domain, description), 2 known-document lookups, 4 document discovery tasks (including `address proof` → `utility bill`), 1 shared-name case, and 1 no-match case. Use the [U.S. advisor workflow sources and example tasks](advisor-search-task-sources.md) to write realistic cases. This is a starter suite, not a sample of production traffic.
2. **Build a synthetic fixture and write the expected outcomes before running search.** Give each case a query, acceptable record IDs, and one sentence explaining why. For `address proof`, seed a usable utility bill and a template that only mentions proof of address; only the bill counts. Use the clues the current `q`-only API actually receives: don't grade the system on picking a specific client's bill when the query gives it no way to do so. Set aside a few tasks for the final comparison and don't tune on them. Use no historical queries, rankings, clicks, or labels.
3. **Run the current engine and the proposed change on the same cases.** Generate fresh results for both. Check **first result** for critical unambiguous client lookups, **any acceptable result in the first five** for document tasks, **both plausible clients in the first five** for the shared-name case, and **empty response** for the no-match case. The existing tests compare unordered sets, so keep them for substring regressions, not ranking decisions.
4. **Review what got better and what broke.** Print the expected and actual top five for each miss. Look for held-out discovery tasks the change fixes, without new failures on agreed critical lookups. For example, don't promote a ranker that finds the utility bill but now puts the wrong client first on an exact-email lookup. No overall score is needed for this first decision.

Use synthetic data only: the current API has no authorization. If real-data use is later considered, verify permissions separately; relevance gains never offset disclosure.

The checklist applies FPF’s **Define What Counts as Better (A.19.ECS)**: use contrasting tasks to decide what counts as success before choosing a measure. See the [research notes](advisor-search-evaluation-notes.md) for the criteria, sources, and when graded ranking or advisor task trials are worth adding.
