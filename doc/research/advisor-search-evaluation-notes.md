# Research notes: evaluating search for financial advisors

For the first run, use the [practical checklist](advisor-search-evaluation.md). These notes explain the criteria and when to extend the benchmark.

**Recommendation.** Define what makes a result safe and useful for the advisor before choosing metrics. Preserve exact lookup and truthful empty results while improving retrieval of usable evidence. Then build a small synthetic benchmark that tests those properties separately. Treat authorization as a separate release gate; use newly observed advisor tasks to check whether better rankings improve the workflow.

**Status:** Not used as direct implementation advice, because of text complexity.

**Framework edition:** [FPF Library on GitHub, revision `11e8d2f`](https://github.com/ailev/FPF/tree/11e8d2feba1dcd0f4253b22a1c026cdbb1804368). Pattern names and section references below refer to this edition.

## 1. What the tests should catch

Don’t promote a ranker that finds a valid utility bill for `address proof` but puts the wrong client first on an exact-email search; if the query gives only a shared name, test whether both plausible clients appear rather than rewarding a guess. The [original substring eval](../../evals/search_quality.py) passed all five cases but checks only which documents were returned. The [Reed ranked eval](../advisor-tasks.md#first-eval-batch-three-tasks) now checks result order and client lookup separately.

## 2. Expand the quality criteria before choosing measures

*FPF patterns: CharacteristicSpace Construction: Define What Counts as Better (A.19.ECS:4.1–4.5) and Improvement-Oriented Quality Evaluation Question Framing (E.22:4.0). The scales and floors below are a local proposal, not an approved release policy.*

**Evaluated object and use.** One version of the Nevis search configuration (code, index and settings), producing a ranked mixed list for existing client records and documents. The engineers' immediate decision is whether to promote a candidate over the baseline for synthetic development. First check task adequacy, then compare improvements without giving up the protected properties. Results hold for the version, frozen fixture, stated client context, effective date and output contract of the test; they do not carry over automatically to another index or workflow. The existing exact-set eval is adequate for fixed substring regressions, not for choosing between ranked systems.

**Derive the properties from decisions the advisor must make.** Work back from opening a client, opening a specific document, choosing usable evidence, and deciding whether to stop looking. For each action, vary one condition while holding the others fixed: target identity, requested artifact, usefulness for the task, or actual existence. If the right repair changes, the criterion should be separate. If the difference does not change the repair, keep it as a slice or diagnostic rather than another score.

- **C1 — Client identity resolution.** On an unambiguous lookup, the independently identified client is first, lower in the returned list, or absent. First is preferred and is the proposed floor for designated critical exact-lookup cases; no special top level is needed above first. An email match on two different clients with the same display name is settled by the target identity, not text similarity. With only an ambiguous name, there is no justified first-place target: the applicable check is whether all fixture-supported candidates remain visible in the inspection window. The evidence is the fixture identity mapping, the clues the system actually received and the emitted order. Without those clues or a target oracle, the unique-target value is **unknown**; known ambiguity uses the separate check, not a miss. Protect against forcing a guess to improve Top-1.
- **C2 — Known-document findability.** For a specified record, judge whether that exact record or an explicitly accepted equivalent is present in the inspection window. Present is preferred and is the floor on critical known-document cases; the first position is the stronger outcome. Same title and perfect textual match do not substitute for the correct client, version or requested period. Evidence is a pre-enumerated set of acceptable fixture IDs and the raw ranked response. An unresolved target/equivalence rule is unknown, not absence. Protect exact record resolution when adding semantic expansion.
- **C3 — Usability for a document discovery task.** For each eligible result, use ordered content judgments: `0` wrong/irrelevant; `1` related but unusable; `2` usable; `3` directly fulfills the task with no additional evidence required. Higher is preferred. A proposed pass for a critical one-proof task requires at least one grade `≥2` in the inspection window; a grade `3` first is exemplary for that task. For a Reed A proof-of-address case, a superseded bill (`1`) is more topical than a bill for another client (`0`), yet neither meets the brief. A permitted current bill that needs routine verification is `2`; a current bill already meeting every stated condition is `3`. Require the client, content and task-specific effective-date or acceptance basis for `2` or `3`. If that basis is missing, record `unjudged`, not `0` or `1`. “Current” belongs here only if the case defines that requirement; do not make recency an independent score that rewards a new but wrong record. Distinguish this judgment from the ranking score used to summarize where usable records appeared.
- **C4 — Correct handling of absence.** On a fixture with an independently certified empty eligible target set and an explicit empty-result contract, the observed response is correctly empty or incorrect. Correct is the floor and top level. Missing fixture coverage or an indexing failure is not evidence of absence; report unknown or an execution error, respectively. Protect positive-case findability: returning nothing for everybody is not a fix.
- **C5 — Completeness when the task needs every item.** Only for tasks with a verified required record set or checklist, use the fraction of required records or slots covered within the fixed inspection depth. Higher is preferred; all mandatory slots is the floor for a task that requires every slot. The evidence must state which record filled which requirement and whether substitution is allowed. Without a complete requirement oracle, corpus-wide completeness is unknown. A single highly ranked proof is enough for C3 but tells us nothing about the missing slots in C5. Keep C5 outside the default assignment benchmark unless a genuine completeness task is in scope.

**Protected conditions, not more relevance points.** Permission is a separate policy claim, checked against a role/record/time oracle and the output surfaces. An unauthorized record fails that gate even if it is clearly the most useful document. No policy oracle or no implemented enforcement is not a pass. Latency is another measured property under a stated load, compared to a budget when one is set; it cannot buy permission or correctness. End-to-end task success is a property of an advisor's attempt with the interface, not of the search engine alone. Measure it separately if we need evidence about the workflow. Semantic similarity, lexical overlap and click frequency are not advisor quality criteria; a matching mechanism or a behavioral trace cannot establish the outcome.

**Test the proposed criteria before relying on them.** Three deliberately contrasting cases give the evaluator independent reference points:

- **Adequate:** one engine puts the exact-email target first, finds the current authorized utility bill within the inspection window for `address proof`, and returns empty on a certified missing-artifact case. On these cases it meets the proposed floors. Putting the bill first can improve the discovery ranking without changing floor adequacy.
- **Below floor, same object kind:** another engine finds the correct proof immediately but puts the wrong client first on the exact-email case or returns a stale substitute on the only-proof case. Both are valid search candidates; neither fixes a failed criterion by scoring higher on the other. A third candidate that omits the only unauthorized hit from its *scored* ranks but still returns it also fails the separate gate.
- **Wrong kind:** a summary generator that receives an already selected document is not a client/document search configuration. Return it for a source-grounded summarization evaluation rather than assigning zero on the search criteria. An API without a UI is not wrong kind for offline ranking; the advisor task test is simply not available yet.

**Result and stop.** For each applicable criterion return `criterion / case or slice / value / short reason / evidence reference`. Cite target and returned rank for C1/C2; for C3 cite the grade, the condition separating it from the adjacent grade, and the relevant fixture span/metadata; for C4 and C5 cite the absence or completeness oracle. Use `meets floor`, `below floor`, `insufficient evidence`, or `out of scope` for the bounded verdict; keep supported readings even when another coordinate is unknown. There is no weighted total. Stop at this scope when critical floors are supported, the semantic comparison is not reversed by an unresolved judgment, and remaining differences cannot change the next development choice. Reopen if the evaluation misses a consequential defect on a new case, misclassifies a difficult but admissible case, or the task/policy changes. The 5/5 exact-set result remains valid for its original fixtures; it is not comparable to the new profile. Use the insertion-order and proof-of-address contrasts to debug the revised evaluation, then check an independently authored holdout before adopting it beyond those examples (A.19.ECS:4.5).

### Check against the existing implementation

**Discriminating check, performed at revision `58790ec`.** In two fresh local `search_factory()` stores, create two synthetic clients named Alex Reed, with distinct `example.com` emails, in opposite insert orders. Attach `May utility bill` to the target. Compare results by fixture keys rather than runtime UUIDs:

| Query | Target inserted first | Distractor inserted first |
|---|---|---|
| `Alex Reed` | target, distractor | distractor, target |
| `alex.target@example.com` | target | target |
| `address proof` | empty | empty |
| `utility bill` | utility bill | utility bill |

Under C1, `Alex Reed` is ambiguous: both stores return both plausible clients, but the default order changes. That difference warrants an eventual disambiguation task, not a fabricated relevance winner. The exact-email clue actually given to the engine produces a unique first-place target in both runs. Under C3, `address proof` misses the assignment's intended utility bill despite C2's literal title query finding it in both runs. These are local contrasts, not estimates of advisor query frequencies.

## 3. Source selection and what transfers

*FPF patterns: Find and Select Sources for a Current Question (F.1:4.2–4.4), Source-Local Meaning Recovery (F.0.1:4.1), and Semantic Synthesis across Source Ontologies (F.0.2:4.1–4.4). Research Method Practice pattern: Decide Whether a Question Needs Research and When to Stop (RMP.1:4.3).*

**Source cut.** The question is what evidence supports the promotion decision in §1. For the maintainer's decision, the source roles below resolve via the named edition, link and passage in each row. The cut is bounded: inspected repo files and primary papers, official benchmark documentation/code, UX practice guidance and the codified rule. No systematic review or best-known-in-field claim is made. The Stanford IR textbook host was unavailable; the NIST definitions and evaluator source supply the relevant operations directly. These sources supply methods and comparators, not evaluation data: no public benchmark queries, rankings, or judgments are imported. Reopen the cut if a local assessor rubric, credible contrary study, new product use, or jurisdiction changes the recommendation.

| Inspected source and passage | Answer-changing contribution | Transfer limit |
|---|---|---|
| **S1.** NIST [TREC English Relevance Judgements](https://trec.nist.gov/data/reljudge_eng.html), working definition and pooling paragraphs; [TREC 2022 Deep Learning Track](https://trec.nist.gov/data/deep2022.html), document vs passage judgment notes | Pair topics, a fixed corpus and qrels (query–result judgments); pool candidate results when exhaustive review is impractical. **Provisional synthesis (F.0.2).** An offline ranking score transfers only against judgments for the *same* task, result identity, eligible corpus and effective date as the run. To see why, keep query text, corpus and ranking unchanged and revoke one advisor's access to the first hit. The score under stale qrels still looks good, but the intended action must change from opening the hit to not seeing it. Keep the ranking and policy fixed and change the assignment from “find a usable proof” to “find every acceptable proof”: the result can still have a perfect first hit but no longer complete the task. The evaluation therefore needs independent policy checks, intent-specific judgments, and a separate observation of task success. None can substitute for the others.

## 4. Turn the criteria into a benchmark

*FPF patterns: Find and Develop a Way to Obtain a Result (C.39:4.2–4.5), Measurement & Metrics Characterization (C.16:5.1–5.6), and Design and Interpret a Method Work Trial (A.3.1.WT:4.1–4.2). This is a candidate procedure, not a qualified trial result.*

Use authored synthetic cases and fresh rankings only. Exclude historical queries, saved result lists, click and session logs, and labels derived from prior retrieval activity.

1. **Fix the task before labeling retrieval.** Use synthetic records now. Start with roughly 30–45 task cases as an engineering budget, not a representative sample: known clients, known documents, semantic document discovery, and explicit negative and ambiguity cases. Seed multiple clients and versions, including hard near-matches. Include name/email/description (including the assignment's partial email-domain match), spelling and Unicode cases, paraphrases and abbreviations, same names and titles, missing artifacts and, when modeled, superseded documents. Use identical wording across different clients for some cases so relevance cannot be decided from keywords alone. Tag which cases are ordinary examples and which isolate a known ambiguity or failure. Reserve whole task/household families for holdout rather than splitting near-duplicate query paraphrases; tune on development cases only.
2. **Join the right objects.** Give each task a stable `task_id`, exact query, intent, stated context, success rule, fixture version and any applicable subject client, role and as-of date. Store which context is passed to the system versus used only by judges; do not expect the current `q`-only API to infer invisible constraints. Give results typed fixture keys, e.g. `client:reed-a`, `doc:reed-a-bill-v2`, and map generated IDs back to them. Record judgment, reason and supporting content/metadata per `(task_id, result_key)` under that task's snapshot. Score the *returned mixed order*, not a reordered list of only the right type. If chunk retrieval is added, capture the evidence span for judging but score at the displayed record level; multiple chunks or duplicate copies must not earn repeated credit for one record.
3. **Keep eligibility out of the relevance scale.** For a future authenticated system, use an independently specified allow/deny matrix for the fixture and time, including a record shared legitimately, one visible only to another advisor/tenant and a revoked grant. In evaluation, check the returned output and any surfaced titles, snippets, counts, suggestions or caches as applicable; a prohibited disclosure fails the policy check even if it is below the rank cutoff. Do not remove such results from a saved run and then report a clean pass. Explicit client/date filters, if introduced, are hard constraints when the contract says so; an authorized but wrong-client item on an unfiltered query is instead a relevance/task error. The current prototype is **synthetic-only**; policy evaluation is not applicable to this API as a passing suite and production use is blocked by missing authorization.
4. **Judge usefulness, then coverage.** On the small fixture, judge all candidates for completeness-required and certified-empty cases and enumerate acceptable IDs where straightforward. For other cases at scale, run substring, lexical and semantic/hybrid candidates on the same authored cases and pool e.g. the top 10 from each fresh run. Deduplicate, add hand-picked known positives and hard negatives, and hide system and rank cues. If a new contender enters the comparison, rerun all contenders and judge any newly surfaced top results before deciding; apply the same judgment version to all contenders. Apply the C3 rubric from §2, with `≥2` counting as usable for binary document success. Keep `unjudged` separate. Have two domain reviewers independently label a shared subset, especially `1` vs `2` and effective-date cases; record disagreements and adjudication. Until a domain reviewer validates them, these are engineering fixture labels, not firm policy.

### Measurement and decision table

| Intended result / unit | Primary measure and denominator | Diagnostic or guard |
|---|---|---|
| **C1:** Correct client for a known identity (task with a unique, independently established target) | **Top-1 accuracy**: fraction of such tasks with the target at rank 1; an absent or lower target is a miss. | MRR@5 (mean `1/rank` for first target at ranks 1–5, zero otherwise); list wrong client at rank 1. For ambiguous names without a known selectable target, use a separate plausible-client coverage test, then a task observation for disambiguation. |
| **C2:** Correct known document (task with a known target record or explicitly accepted equivalents) | **Success@5**: fraction with at least one acceptable result in the first five. | MRR@5; separate failures by wrong client, wrong period or wrong version. Keep this slice distinct from semantic discovery. |
| **C3:** Useful semantic documents (positive discovery task with at least one judged usable result) | **nDCG@5**: normalize discounted top-five gain by the ideal top five from the same judged pool. Choose gains `0, 0, 2, 3` for labels `0–3`, so merely related records cannot inflate utility. In `trec_eval`, map grades to gains for the nDCG input and preserve the original rubric separately. | Also show Success@5 and judged coverage in the first five **returned** positions (report short lists separately). For exploratory computation unjudged has zero observed gain, not assessed `0`; if unjudged top hits could change the comparison, label or return inconclusive. `bpref` with `≥2` binary threshold is an optional incomplete-judgment diagnostic. |
| **C5:** Collect all required evidence (task with a verified complete set or checklist) | **Recall@k** for unique required records, or fraction of checklist slots filled by distinct acceptable evidence as the task specifies. Fix `k` first. | Without completeness, label the denominator “known judged positives,” not corpus recall. Use slot coverage for substitutable proofs; duplicates cannot fill a slot twice. |
| **C4:** Nothing eligible/useful exists (certified negative task) | **False-positive task count/rate** under the agreed output contract; for a certified empty response case, success is `200 []`. | Distinguish no match in the snapshot from an upstream error, indexing lag or invalid `q`. Do not mix these tasks into positive-task rank means with undefined ideal gain. |
| **Separate workflow check:** Correct/safe advisor action (task attempt) | **Verified task success**: opens the intended client or selects acceptable evidence, or correctly recognizes no usable evidence. | Report wrong-client/obsolete selections, time to correct completion among successes with its denominator, task timeouts/failures separately, and reformulations. Compare service p95 latency separately at stated corpus size, concurrency and warm/cold conditions. |

**Worked scoring example (illustrative, not run).** For the scoped task `address proof` for Reed A as of June 1, suppose the judged pool has one current acceptable bill (grade `3`), one superseded bill (grade `1`) and one bill for another client (grade `0`, visible to the advisor but wrong for this task). Returning `[other client, superseded, current]` gives Success@5 = 1 and nDCG@5 = `(3 / log₂(4)) / 3 = 0.50`; `[current, other client, superseded]` gives the same Success@5 and nDCG@5 = `1.00`. If the other client's bill is **not** visible under the applicable policy, neither list is a passing output. If the task changes to gathering evidence for several checklist slots, these scores cannot answer whether every slot was filled.

Five is an initial inspection budget, not a claim about UI behavior. Set the cutoff from intended use once a UI exists. Report counts, denominators and macro means by intent and important slice, not a blended “search quality” number. If several variants come from one scenario, report dependence (or use scenario-level aggregation/resampling). Publish paired wins/ties/losses and concrete regressions; for larger holdouts, uncertainty on paired differences can be estimated by resampling independent task families. A small hand-built suite does not support a population confidence claim.

## 5. How to use the evidence

**Next change decision.** Keep the five smoke cases and add a separate versioned benchmark under `evals/`. Compare the current substring implementation, a field-aware lexical baseline (e.g. BM25 plus exact-field priority) and a semantic or hybrid candidate when available. Freeze corpus, task IDs, judgments, cutoff/gains, and entitlement/time assumptions for paired evaluation. Preserve actual response order and tie-breaking behavior; don’t “fix” ties in the evaluator. Report per-task differences and candidate misses separately from reranking misses if candidate-stage traces exist. A gain over substring alone does not show that semantic retrieval is worth its added cost if the lexical comparator closes the gap.

**Proposed decision rule, not an approved threshold.** A verified policy violation blocks real-data release, and a new failure on an agreed critical exact-lookup case blocks promoting the candidate until investigated. Missing entitlement or decision-changing judgment coverage means insufficient evidence, not a pass. For synthetic development, prefer a contender that fixes multiple held-out semantic task failures without new critical regressions and stays within the agreed resource budget. If the comparison depends on one label, a thin slice, or a contested gain mapping, review those cases or keep the simpler baseline; don't declare a winner from the aggregate. Maintainers choose the development candidate; the relevant data/security owner must approve any real-data gate and the product owner sets acceptable quality and latency trade-offs.

**Advisor trial only when it answers the remaining question.** If a viable candidate improves rank and there is a usable interface, ask a small set of advisors or operations specialists to perform matched synthetic tasks. Counterbalance order and use equivalent variants to reduce learning. Keep the interface constant if attributing a difference to ranking; otherwise report a whole-workflow comparison. Use ordinary success cases plus discriminating ones (duplicate names, an expired but highly topical document, and no available proof). Let participants search naturally rather than supplying the ranked-eval query. Capture actual actions, outcome verified against case criteria, supported aids, time, deviations and the reason a participant gives separately. Stop a session on disclosure or at the predeclared task time limit. A handful of newly conducted sessions can diagnose friction; it cannot establish a deployment effect. Keep the trial on synthetic records and use only observations collected for the trial. If summaries are added, test source support, attribution and material omissions separately from retrieval.

**Evidence return and stop.** Apply Evidence Graph Referring: Claim-Bound Evidence and Provenance Graph (A.10:4.1–4.6) and Make Advice and Evidence Demands Worth Their Burden (C.11.DUA:4.1–4.2). Save corpus/task/qrel revisions, assessor rubric and adjudication records, role/policy snapshot where applicable, engine/index/scorer versions, raw ranked fixture IDs, metric settings, run date, deviations and per-case outcomes. This lets the maintainer trace a claim such as “improved semantic nDCG@5 on holdout v1” back to actual run results and judgments, rather than to a commit trailer or a planned trial. The cheap next evidence is a synthetic ranked comparison: it can change the engine choice without access to client data. Add assessor time where disagreements could change that choice; do not build a broad benchmark just to fill gaps. Reopen only affected claims when the corpus, advisor workflow, rubric, policy, date semantics or display changes. The current evidence justifies preserving the smoke suite and building the ranked benchmark; it does not select an engine or authorize a pilot with client records.
